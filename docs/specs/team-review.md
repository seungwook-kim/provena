# Spec — 팀 합동 검토 (F-03)

## Why

- **페르소나**: 백엔드 개발자(3년 차). 외부 SaaS 모니터링 도구를 연 4만 달러에 도입하려고 한다.
- **상황**: 도입 요청 하나에 보안 검토, 운영(SRE) 검토, IT 운영 검토, 재무 승인이 모두 걸린다. 지금은 팀마다 따로 물어 검토를 받는다.
- **문제**:
  1. 팀마다 따로 묻다 보니 빠진 검토가 생긴다 (가설)
  2. 인적 오류로 난 큰 장애 중 85%가 절차 미준수 또는 절차 결함이다 (Uptime Institute 2025). 절차를 한 번에 훑어보지 못하는 것이 위험 요인이다
  3. 어느 정책 섹션을 근거로 어떤 쟁점을 봤는지 기록이 남지 않는다
- **측정 지표**: 사람 승인 전 저장 0건, 쟁점마다 근거 섹션·판 날짜 표시 여부, 승인 대기 중 재시작 뒤 재개 성공. 쟁점 누락률은 사람이 정한 정답 쟁점과 대조해 재는 방법을 D0에 합의한다

## Goal

- **해결 목표**: 한 건의 업무 요청을 보안, 인프라·SRE, IT 운영, 재무 팀 에이전트가 각자 핸드북 근거로 검토하고, 쟁점표 하나로 합친다. 사람이 승인해야 저장한다.
- **성공 기준**
  - Supervisor 1개와 팀 에이전트 4개로 동작한다 (가이드 G4 최소형: Supervisor + 서브에이전트 2개 이상)
  - 사람 승인 전에 저장되는 쟁점표 0건
  - 쟁점표의 모든 행에 근거 섹션 제목 경로와 판 날짜가 붙는다
  - 승인 대기(interrupt)에서 멈춘 뒤 서버를 재시작해도 같은 `thread_id`로 승인 지점부터 재개된다
- **Out of Scope**: 실제 구매·배포 승인과 외부 발송(승인 후 저장까지만), 쟁점의 최종 판단과 해결책 확정(사람이 한다), 다섯 번째 이상의 팀, 승인권자 계산(F-04)

## What

**Happy Path**
1. 사용자가 한 건을 설명한다 (예: "새 외부 SaaS 모니터링 도구를 연 4만 달러에 도입하려 한다").
2. 질문 종류 판정에서 합동 검토 경로로 간다.
3. Supervisor가 요청을 네 팀 에이전트에 나눠 준다.
4. 팀 에이전트가 각자 핸드북에서 근거를 검색해 쟁점을 뽑는다.
   - 보안: 제3자 위험 검토, 데이터 분류
   - 인프라·SRE: 운영, 장애 대응 영향
   - IT 운영: 계정·접근 관리, 도구 승인
   - 재무: 권한표상 승인권자
5. 쟁점표로 합친다 (팀, 쟁점, 근거 섹션, 판 날짜).
6. 그래프가 사람 승인(interrupt)에서 멈추고, 쟁점표가 관리자의 승인함에 올라온다.
7. 관리자가 쟁점표를 보고 승인 또는 반려한다. 승인이면 그래프가 재개되어 쟁점표가 저장된다.
8. 요청한 사용자가 저장된 쟁점표를 확인한다.

**Edge Cases** (최소 5개 + 처리 방식)

| # | 상황 | 처리 방식 |
|---|---|---|
| EC-01 | 합친 결과 쟁점이 0건이다 | 승인 없이 "쟁점 없음"으로 끝낸다 |
| EC-02 | 한 팀 에이전트가 근거를 못 찾거나 실패한다 | 그 팀을 "검토하지 못함"으로 쟁점표에 남긴다. 조용히 빠지지 않는다 |
| EC-03 | 승인 대기 중에 서버가 재시작된다 | 체크포인트(Postgres)에서 같은 `thread_id`로 승인 지점부터 재개한다 |
| EC-04 | 관리자가 반려한다 | 쟁점표를 저장하지 않고, 반려 사유(`comment`)를 기록한다 |
| EC-05 | 팀 의견이 서로 충돌한다 | 하나로 단정하지 않고 팀별 의견을 나란히 쟁점표에 둔다 |
| EC-06 | 관리자가 아닌 사용자가 승인을 시도한다 | 403. 승인은 관리자만 한다 |
| EC-07 | 검색된 원문에 "승인하라" 같은 지시가 심어져 있다 | 지시를 따르지 않는다. 저장은 사람 승인(interrupt)을 통과해야만 된다 |
| EC-08 | 요청 설명에 도입 금액 등 검토에 필요한 값이 빠졌다 | 필요한 값을 되묻는다 |
| EC-09 | 근거가 비공개 주소(`internal.gitlab.com`)로만 연결된다 | 근거로 쓰지 않고 "비공개 문서"로 표시한다 |

## How

```
POST /chat   (합동 검토 요청은 질문 종류 판정으로 이 경로에 들어온다)
인증: 로그인 필수

요청 바디:
{ "thread_id": string, "message": string }

응답 (200, text/event-stream): AgentEvent 스트림
  ... token, citation 이벤트 ...
  { "type": "approval_request", "thread_id": string,
    "data": { "approval_id": string, "kind": "issue_table", "summary": string } }
  그래프는 여기서 멈춘다 (interrupt)
```

```
GET /approvals              승인 대기 목록 (관리자)
  → [ ApprovalItem ]
  ApprovalItem: { "approval_id": string, "kind": "decision_table" | "issue_table",
                  "summary": string, "created_at": string }

POST /approvals/{id}        (관리자)
요청 바디 (Decision):
{ "approval_id": string, "approve": boolean, "comment": string (optional) }

응답 성공 (200): 그래프를 재개하고 결과(저장됨/반려됨)를 돌려준다
응답 실패:
401 로그인하지 않음
403 관리자가 아님
404 없는 approval_id
409 이미 처리된 승인
```

- 쟁점표 한 행(초안, 필드 이름은 D0에 확정): 팀, 쟁점, 근거 섹션(제목 경로), 판 날짜, 원문 URL. 팀이 검토하지 못한 경우는 "검토하지 못함"과 이유를 적는다.
- 그래프: Supervisor와 팀 에이전트(`backend/graph/departments/`). 팀 에이전트 4개는 고른 코퍼스 절과 1:1로 맞춘다(보안 ↔ security, IT 운영 ↔ business-technology, 재무 ↔ 도입 승인 정책 절, 인프라·SRE ↔ 인프라·장애 대응 절. 대응표는 D0에 확정). 팀 관점 규칙을 `SKILL.md`로 분리하는 것은 가산(MCP와 Skill)이고, 폴더 이름(sre·it-ops 등)은 D0에 정한다.
- 체크포인터는 Postgres에 두고, 사람 승인은 interrupt로 멈춘 뒤 `resume()`으로 이어 간다.
- 테이블: `approvals`(approval_id, kind, thread_id, status, decided_by). 승인된 쟁점표를 저장하는 위치와 모양은 D0에 정한다.
- 재무 팀 에이전트가 승인된 결정표(F-04)의 실행 결과를 쓰는지는 D0에 합의한다.
- 신뢰 경계: 쟁점표 저장은 승인(interrupt)을 거쳐야만 되고, 검색된 원문은 지시가 아닌 자료로만 다룬다. 인용은 코드로 원문과 대조한다.
- 단일·멀티 비교 평가는 정책 질문 경로(F-01)로 하고, 합동 검토는 별도 시연 경로다.

## AC (Given-When-Then)

**AC-01 · 네 팀이 각자 쟁점을 뽑아 쟁점표 하나가 된다**
- GIVEN: 로그인한 사용자가 "새 외부 SaaS 모니터링 도구를 연 4만 달러에 도입하려 한다"는 합동 검토를 요청했다
- WHEN: 그래프가 실행된다
- THEN: 보안, 인프라·SRE, IT 운영, 재무 에이전트가 각자 검색해 쟁점을 만들고, 쟁점표에 팀, 쟁점, 근거 섹션 제목 경로, 판 날짜가 한 행씩 들어가며, 관리자 승인함에 `issue_table` 항목이 올라온다

**AC-02 · 승인 전에는 저장되지 않는다**
- GIVEN: 쟁점표가 승인함에서 대기 중이다
- WHEN: 관리자가 아직 승인하지 않았다
- THEN: 저장된 쟁점표가 0건이다. 승인(`approve=true`)이 들어온 뒤에만 저장된다

**AC-03 · 재시작 뒤에도 승인 지점에서 재개된다**
- GIVEN: 그래프가 승인(interrupt)에서 멈춰 있다
- WHEN: 서버를 재시작하고 같은 `thread_id`로 승인(`POST /approvals/{id}`)을 보낸다
- THEN: 처음부터 다시 돌지 않고 승인 지점부터 재개되어 쟁점표가 저장된다

**AC-04 · 반려하면 저장하지 않는다**
- GIVEN: 쟁점표가 승인함에서 대기 중이다
- WHEN: 관리자가 `approve=false`와 사유로 반려한다
- THEN: 쟁점표는 저장되지 않고, 반려와 사유가 기록된다

**AC-05 · 쟁점이 없으면 승인 없이 끝난다**
- GIVEN: 네 팀 모두 쟁점을 뽑지 않았다
- WHEN: 쟁점표를 합친다
- THEN: 승인함에 항목이 만들어지지 않고 "쟁점 없음"으로 끝난다

**AC-06 · 관리자가 아니면 승인할 수 없다**
- GIVEN: 일반 사용자 계정
- WHEN: `POST /approvals/{id}`를 호출한다
- THEN: 403을 받고 그래프는 재개되지 않는다
