### I-06 근거

1. `/health` 처리기는 호출될 때만 움직인다: `backend/main.py:387~398`. `DATABASE_URL` 이 있고 마지막 `SELECT 1` 이후 600초(`KEEPALIVE_SECONDS`, `main.py:93`)가 지났으면 응답을 보낸 뒤 백그라운드로 `ping_database()`(`main.py:260~269`, `SELECT 1`)를 한다. 스스로 도는 타이머는 없고, 마지막 시각은 프로세스 메모리(`keepalive` 사전, `main.py:384`)에 있어 인스턴스가 새로 뜨면 초기화된다.
2. 정시 실행은 `.github/workflows/handbook-sync.yml:9` 하나뿐이다(`cron: "7 18 * * *"`, 매일 03:07 KST). `ci.yml`, `secret-scan.yml` 에는 `schedule` 이 없다(`grep cron|schedule` 결과). 이 워크플로는 `/health` 를 부르지 않고 `backend.rag.ingest.schedule --once`(43줄)로 `secrets.DATABASE_URL` DB에 직접 붙는다.
3. README Cloud Run 절의 배포 명령(`README.md:172`)에는 `--max-instances 1` 만 있고 `--min-instances` 는 없다. 그러면 Cloud Run 기본은 0이라 요청이 없으면 인스턴스가 내려간다(일반 지식, GCP 콘솔 설정은 확인 못 함). A-14의 35초 응답이 이와 맞는다.
4. 그 밖에 외부 감시(업타임 모니터, Cloud Scheduler 등)가 있는지는 저장소에서 찾을 수 없었다(`grep` 에 `Scheduler`, `min-instances`, `ping` 없음, 운영 문서 `docs/` 에도 없음).

의미(K-15와 연결): 정시 실행을 꺼 두면(진형 결정: 주말 내내와 동결 후에도 비활성) 지금 DB를 정기적으로 건드리는 유일한 자동 주체가 사라진다. 그러면 `/health` 를 누가 부르지 않는 한 `SELECT 1` 도 나가지 않아 Supabase 무료 플랜의 비활성 정지(정지 기준 기간은 확인 못 함) 위험이 남고, 인스턴스는 꺼진 채라 발표 첫 요청이 약 35초 걸릴 수 있다. 정시 실행이 켜져 있던 동안 DB가 깨어 있던 것은 부수 효과였고 `/health` 와는 무관했다.
