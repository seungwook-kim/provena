### 1. Flaky 테스트 파일은 언제까지 고쳐야 하나?

**식별된 시점부터 24시간 이내에 수정 사항을 배포해야 합니다.**

- 24시간 내 수정하지 못하면 해당 이슈는 Severity 3 프로덕션 인시던트로 에스컬레이션됩니다.
- 수정이 어려우면 테스트를 quarantine(격리)할 수 있습니다.
- Fast quarantine은 최대 3일입니다.
- Long-term quarantine은 최대 3개월입니다.
- 3개월이 지나면 테스트 삭제 절차가 시작되며, 삭제 MR을 처리할 수 있는 마지막 기간은 1주일입니다.

격리했다고 문제가 해결된 것은 아닙니다. 담당자는 근본 원인을 조사하며 매주 진행 상황을 업데이트해야 합니다.

### 5. dbt 모델 SQL에서 서브쿼리를 써도 되나?

**사용할 수는 있지만, GitLab Data Team 스타일 가이드는 CTE를 우선적으로 사용할 것을 권장합니다.**

즉, 서브쿼리를 무조건 금지하는 것은 아니지만 CTE(Common Table Expression)를 사용하면 가독성과 성능 측면에서 유리하다는 것이 가이드의 방향입니다.

권장 방식 – CTE

```sql
WITH important_list AS (
    SELECT DISTINCT
        specific_column
    FROM other_table
    WHERE specific_column != 'foo'
)

SELECT
    primary_table.column_1,
    primary_table.column_2
FROM primary_table
INNER JOIN important_list
    ON primary_table.column_3 = important_list.specific_column
```

비권장 방식 – 서브쿼리

```sql
SELECT
    primary_table.column_1,
    primary_table.column_2
FROM primary_table
WHERE primary_table.column_3 IN (
    SELECT DISTINCT specific_column
    FROM other_table
    WHERE specific_column != 'foo'
)
```

추가 스타일 규칙:

- CTE는 쿼리 최상단에 배치합니다.
- 다른 테이블을 참조할 때 CTE를 사용합니다.
- CTE 하나는 가능하면 하나의 논리적 작업만 수행하도록 합니다.
- CTE 이름은 짧고 의미 있게 작성합니다.
- 여러 모델에서 중복되는 CTE는 별도 dbt 모델로 분리합니다.
- SQLFluff를 사용해 SQL 스타일을 검사합니다.

근거: GitLab Handbook – SQL Style Guide / GitLab Handbook – dbt Guide

### 6. 같은 벤더와 60일 이내에 추가 계약을 하면 승인 금액은 어떻게 계산하나?

이 항목은 공개된 GitLab Handbook 자료만으로는 60일 합산 규칙의 정확한 적용 방식까지 확인할 수 없습니다.

다만 계약 승인과 관련해 확인되는 원칙은 다음과 같습니다.

- 기존 계약과 추가 계약을 별개의 구매로 취급할 수 있는지 Procurement의 확인이 필요합니다.
- 계약 금액과 실제 구매 요청 금액이 일치해야 합니다.
- 승인 한도를 피하기 위해 하나의 구매를 여러 계약으로 인위적으로 분할하는 것은 정당한 승인 절차를 대신할 수 없습니다.
- 추가 계약은 기존 계약의 변경 또는 추가 구매로 처리해야 하는지 확인해야 합니다.

따라서 60일 내 추가 계약에 대해 기존 계약 금액과 신규 계약 금액을 합산하는 구체적인 규칙이나 예외는 내부 Procurement 정책을 확인해야 합니다. 임의로 계약을 쪼개서 승인받는 방식은 권장할 수 없습니다.

근거: GitLab Handbook – Procurement

### 7. 외부 SaaS 계약 금액이 10,000달러라면 업무 승인자와 재무 승인자는?

**공개 Handbook에서 확인되는 승인 절차는 다음과 같습니다.**

| 승인 구분 | 담당 |
|---|---|
| 업무 승인 | 해당 구매를 요청하는 Functional 조직의 승인권자 |
| 재무 검토 | FP&A |
| 구매 검토 | Procurement |
| IT 검토 | 신규 소프트웨어 구매이므로 IT 검토 필요 |

10,000달러는 25,000달러 미만이므로 공개된 Procurement 정책상 신규 구매에 대한 RFP 입찰은 필수 사항이 아닙니다.

다만 업무 승인자와 재무 승인자의 정확한 개인별 직책 및 승인 금액 한도는 GitLab 내부 Signature Authorization Matrix에 따라 결정됩니다.

근거: GitLab Procurement Process / GitLab Accounting and Reporting

### 8. 외부 SaaS 계약 금액이 30,000달러라면?

10,000달러와 마찬가지로 업무 조직과 재무 조직의 승인이 필요하지만, 구매 절차에 차이가 있습니다.

| 승인·검토 구분 | 담당 |
|---|---|
| 업무 승인 | 해당 Functional 조직의 승인권자 |
| 재무 검토 | FP&A |
| 구매 검토 및 협상 | Procurement |
| IT 검토 | IT |
| 추가 보안 검토 | SaaS 및 데이터 접근 여부에 따라 Security |

**10,000달러와 달라지는 핵심은 Procurement 협상 의무입니다.**

GitLab Procurement 정책은 다음을 명시합니다.

- SaaS 계약이 25,000달러를 초과하면 Procurement가 계약 협상을 담당합니다.
- 25,000~100,000달러의 신규 구매는 Business-led quick-bid 대상이며, 2개 업체의 견적이 필요합니다.
- 최종 구매 승인에는 해당되는 경우 FP&A, Functional 및 Executive 승인이 포함됩니다.

따라서 30,000달러 SaaS 계약은 2개 업체 견적 및 Procurement 협상 절차를 고려해야 합니다.

정확한 개인별 업무·재무 승인자는 내부 승인 매트릭스 확인이 필요합니다.

근거: GitLab Handbook – Procurement Process

### 9. GitLab 정기 릴리스와 패치 릴리스 일정은?

[공식 릴리스 정책 확인]

| 구분 | 주기 | 일정 |
|---|---|---|
| Monthly Release | 월 1회 | 매월 세 번째 목요일 |
| Scheduled Patch Release | 월 2회 | 정기 릴리스 전후의 수요일 |
| Out-of-band Patch | 필요시 | 긴급 수정 및 SLO에 따라 별도 배포 |

추가 설명:

- Monthly Release는 새로운 기능, 버그 수정 및 성능 개선을 포함합니다.
- Patch Release는 기존 버전의 버그 수정과 보안 업데이트를 제공합니다.
- 정기 패치 릴리스는 월 2회가 목표이며, 운영 상황에 따라 일정이 변경될 수 있습니다.
- 긴급 릴리스는 정기 일정과 별도로 추가될 수 있습니다.

예를 들어 월간 릴리스가 세 번째 목요일에 진행된다면, 패치 릴리스는 그 전후 수요일을 목표로 합니다.

근거: GitLab Handbook – Monthly Releases / GitLab Handbook – Patch Releases

### 10. Severity 1 인시던트 종료 후 공개 RCA와 리뷰 마감 기한은?

**공개 RCA는 인시던트 해결 후 7일 이내, Incident Review는 해결 후 5영업일 이내가** 공개 Incident Review 정책에 명시된 기준입니다.

| 항목 | 마감 기한 |
|---|---|
| Public RCA | 해결 후 7일 이내 |
| Incident Review 종료 | 해결 후 5영업일 이내 |

세부 사항:

- Severity 1 인시던트는 공개 RCA가 필요합니다.
- 공개 RCA 작성과 게시 책임은 DRI(Directly Responsible Individual)에게 있습니다.
- 내부 리뷰에 고객 식별 정보, 보안 민감 정보 등이 포함되면 공개 가능한 버전을 별도로 작성해야 합니다.
- Incident Review는 RCA 작성뿐 아니라 시정 조치(Corrective Actions) 생성 및 담당 팀 배정, Bar Raiser 승인도 완료해야 종료할 수 있습니다.
