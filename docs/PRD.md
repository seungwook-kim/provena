# Provena PRD

IT 조직의 정책·런북을 근거로 답하고, 정책이 바뀌면 이미 나간 답을 다시 검증해 정정을 보내는 엔지니어링 지식 AI 플랫폼의 요구사항 문서다.

| 항목 | 내용 |
|---|---|
| 조원 | 3조 / 김승욱(팀장), 박진형, 강경희 |
| 서비스명 | Provena (프로베나) |
| 근거 문서 | 3차 팀 프로젝트 가이드 v5 (이하 "가이드") |
| 산업 | IT·플랫폼. 제품은 기업용 엔지니어링 지식 AI 플랫폼이고, 시연 데이터는 실제 IT 회사(GitLab, 오픈소스 회사)가 공개한 핸드북이다. 가이드 p.8의 IT·플랫폼 예시(프레임워크·오픈소스 문서 RAG)와는 넣는 문서 종류가 다르다. p.8은 "기본으로" 권하는 예이고 금지 조건은 아니다 |

## 1. 개요

개발 조직이 쓰는 엔지니어링 지식 AI 플랫폼이다. 조직의 정책·런북을 넣으면, 사용자가 업무 중에 묻는 "이 건은 누가 승인하고, 어떤 절차를 따르나"에 정책 원문의 섹션과 판(날짜)을 인용해 답한다. **정책이 바뀌면, 바뀐 섹션을 근거로 이미 나간 답을 다시 검증해 그 답을 받은 사람과 업무시스템에 정정을 보낸다.** 승인 권한표는 결정표로 바꾸고, 사람이 승인한 표만 판단에 쓴다.

- 시연은 GitLab 공개 핸드북(CC BY-SA 4.0)으로 한다. 실제 IT 회사가 쓰는 정책이고, git 이력에 실제 개정 기록이 남아 있다.
- 도입 기업은 자기 문서(Markdown·위키)를 같은 적재 파이프라인에 넣어 쓴다. 문서가 git에 없어도 된다. 위키 페이지 이력처럼 두 시점의 문서 묶음을 섹션 단위로 비교해 변경을 찾는다(F-07).
- 사용자는 볼 권한이 있는 문서만 근거로 답을 받는다(F-06, 계획). 동결(2026-11-16) 시점에는 검색 단계 거르기가 구현되지 않았고 리콜 알림 쪽 확인까지만 있다(아래 F-06 행과 가산 문단).
- 플랫폼은 REST API, SDK, MCP, 웹훅으로 연결하므로, 회사 업무시스템이 Java든 Python이든 붙일 수 있다.
- 질문과 문서는 한국어·영어 어느 쪽이어도 된다(다국어 임베딩과 한국어 토큰 BM25). 시연 코퍼스는 영어 핸드북이다.

## 2. 문제 정의

| 구분 | 내용 |
|---|---|
| 지금 하는 방식 | 위키·핸드북을 검색하거나 슬랙으로 담당 팀에 묻는다. AI 챗봇을 들여도 문서를 찾아 보여 주는 데서 멈춘다 |
| 불편한 점 | 답을 찾는 데 시간이 들고, 담당자 답을 기다리며 흐름이 끊긴다. 정책·런북이 바뀌어도 예전에 받은 답(AI 답 포함)은 그대로 남아, 바뀐 절차를 모르고 일하게 된다 |
| 범용 챗봇의 한계 | 정책의 어느 판을 근거로 했는지 밝히지 않는다. 예전에 한 답을 추적하거나 고치지 않는다 |

**근거**

| 근거 | 수치 | 출처 |
|---|---|---|
| 답을 찾는 시간 | 개발자의 약 60% 이상이 하루 30분 넘게 답을 찾는 데 쓴다. 지식 사일로를 주 10회 이상 겪는 비율 29.6%, 답변 대기로 흐름이 끊긴다는 동의 약 53% | Stack Overflow 2024 설문 (해당 문항 28,911명, https://survey.stackoverflow.co/2024/professional-developers , 2026-11-13 확인. 본문의 61%와 차트 구간 합 63.8%가 소폭 달라 "약 60% 이상"으로 적었다) |
| 조직 비효율 | 개발자 50%가 주 10시간 이상을 잃는다. 정보 찾기(서비스·문서·API)가 주요 원인으로 나열됨 | Atlassian Developer Experience 2025 (3,500명, 6개국) |
| 문서 신뢰 | 개발자 포털 정보 갱신이 주 1회 이하 53%, 정확성 의심 50%, 완전 신뢰 3% | Port 2025 State of IDP (표본 수 미공개) |
| 절차 문제 | 인적 오류로 난 큰 장애 중 85%가 절차 미준수 또는 절차 결함 | Uptime Institute 2025 보도자료 |
| AI 답 불신 | AI 사용·사용 예정 84%, 정확성 불신 46%, "거의 맞지만 틀린 답"이 가장 큰 불만 66% | Stack Overflow 2025 설문 (49,000명 이상) |

- "낡은 런북이 장애를 일으켰다"는 직접 통계는 없다. 절차 문제(Uptime)와 AI 답 불신(Stack Overflow 2025)을 이어서 "바뀐 정책을 반영하지 못한 답"의 위험을 주장하는 것은 **추론**이다.
- 국내 개발자 대상 지식 검색 시간을 다룬 공개 설문은 찾지 못했다. 팀이 직접 받은 현직자 설문(2026-11-13 배포, 11/15 회신 마감)은 현직 개발자 1명이 응답했다. 2주 동안 규정·절차를 몰라 물은 횟수는 1~2회, 질문을 받은 횟수는 3~5회였다(주 0.75회, 2회로 환산). 건당 해결 시간은 10분 미만~30분, 2주 동안 찾거나 묻는 데 쓴 시간은 0.25~0.75시간이다. 자주 묻는 주제 3개 중 2개(경비·법인카드, 구매·결재선)가 이 서비스가 다루는 주제다. 응답이 1명이라 비율 대신 "1명 중 1명"으로 적고, 편의 표본이며 기억에 의존한 자기 보고라 대표성이 없다. 설문 문항은 [docs/deliverables/survey/questionnaire_2026-11-13.md](./deliverables/survey/questionnaire_2026-11-13.md), 응답 요약은 [docs/deliverables/survey/responses_summary.md](./deliverables/survey/responses_summary.md)에 있다.
- **정책이 바뀌는 빈도 실측**(2026-11-13, 공개 API 읽기만, 비용 0원). GitLab 핸드북 저장소(`gitlab-com/content-sites/handbook`, id 42817607)를 2025-11~2026-10 12개월(평일 260일) 집계했다(실행 UTC 2026-11-13 04:38, 호출 간격 0.7초). 병합 MR이 4,018건(월 평균 335건, 월 최소 261건(2026-08), 월 최대 435건(2026-02), 평일 하루 약 15.5건), 생성 MR이 5,070건(평일 하루 약 19.5건)이다. 정책 경로를 건드린 커밋은 보안 386건(평일 하루 약 1.5건), 법무 114건, IT·ETA 63건, 재무 62건, 인사정책 19건이다. 2026-10 병합 322건의 작성자는 170명(자동 계정 2건 포함)이다. **이 수치는 정책·문서가 바뀌는 빈도의 실측이며, 사람이 정책 질문을 하루에 몇 번 하는지의 실측이 아니다.** 리콜(변경 추적)이 받을 입력량의 근거로만 쓰고, 질문 빈도는 계속 가설로 둔다(12장 "사용 빈도" 행). 커밋은 경로를 건드린 커밋이라 MR과 1:1이 아니다. 2026-07 이후 IT·ETA 증가는 경로 개편 영향일 수 있으나 확인하지 못했다. 같은 조사에서 접근 요청 트래커(`gitlab-com/team-member-epics/access-requests`)는 API 404, 웹 403(비공개)이라 셀 수 없었고, 공개 gitlab-com 그룹에서 제목에 "access request"가 든 이슈는 12개월 7건뿐이었다. 원자료와 집계 스크립트: `evals/results/market_evidence_20261113/`(`raw_counts.json`, `count_gitlab.ps1`, `raw_authors_oct2026.json`, `count_authors_oct.ps1`).
- 실무자의 불편은 외부 검토자 1명(가이드 p.14의 외부 시선)에게 확인받았다. 외부 검토자는 위 설문의 응답자인 현직 개발자 1명이다(2026-11-13 배포, 11/15 회신). 응답자는 2주 동안 규정·절차를 1~2회 묻고 3~5회 질문을 받았으며, 건당 해결 시간은 10분 미만~30분이라고 답했다.
- 같은 설문에서 받은 답에 근거 문서가 함께 오는 경우는 "거의 없음"(1명 중 1명)이었고, 근거를 붙여 답하는 도구를 "써 보겠다"고 답했다. 도구에서 가장 중요한 것은 정확한 근거와 메신저에서 바로 쓰는 것이었다.

**기획 배경:** 팀장 김승욱은 SI 개발자로 4년 7개월(2020.10~2025.04) 일했다. 고객 시스템을 개발하며 산출물·승인 절차와 감리·감사 대응을 겪었다. 이 경험에서 "근거 문서를 붙여 답하고, 기준이 바뀌면 다시 알려 주는 도구"를 기획했다.

## 3. 목표와 비목표

**목표**
1. 정책 원문을 근거로, 섹션을 인용하고 판 날짜를 붙여 답한다.
2. 정책 변경을 감지하고, 영향받는 과거 답변을 찾아 받은 사람에게 알린다(답변 리콜). 링크로 연결된 다른 정책은 관리자에게 함께 볼 후보로 알린다.
3. 한 건의 업무를 여러 팀 관점에서 검토한 쟁점표를 만들고, 사람이 승인해야 저장한다.
4. 승인 권한표를 결정표로 바꾸고, 사람이 승인한 결정표만 업무시스템에서 실행한다.
5. 가이드의 필수 조건 G1~G7을 모두 충족한다.

**비목표**
- 최종 판단을 대신하지 않는다. 최종 결정은 사람이 한다.
- 실제 구매·배포 승인이나 외부 발송은 하지 않는다. 승인 후 저장까지만 한다(가이드 p.7).
- 파인튜닝은 하지 않는다.
- GitLab의 비공개 문서는 다루지 않는다.

## 4. 사용자

| 구분 | 누구 | 하는 일 |
|---|---|---|
| 주 사용자 | 개발 조직의 개발자, SRE·DevOps, 보안·IT 운영 담당 | 정책 질문, 도입·배포 전 검토, 리콜 알림 확인 |
| 두 번째 사용자 (정책 담당자) | 정책 관리 담당(플랫폼팀·보안팀·재무), 문서 소유자. 관리자 역할을 겸한다 | 개정안을 올리기 전에 영향받을 답·결정표·사람을 확인(F-05), 리콜 결과 확인, 결정표 승인 |
| 지불 주체 | 엔지니어링 조직(개발 생산성·플랫폼 엔지니어링 예산, 결재는 VP Engineering 또는 엔지니어링 디렉터) (**가설**) | 엔지니어링 지식 AI 플랫폼 도입 |

**정책 담당자를 두 번째 사용자로 둔 이유 (2026-10-29):** 정책 질문은 한 사람이 하루 몇 번 정도라, 채팅으로 끌어오는 방식만으로는 슬랙에 묻는 습관을 이기기 어렵다(가설). 정책을 고치는 사람은 개정할 때마다 "누가 예전 기준으로 일하는가"를 알아야 한다. 그래서 주 사용자(개발 조직)는 그대로 두고, 같은 IT·플랫폼 조직의 정책 담당자에게 개정 전 MR 댓글로 영향을 보여 주는 경로(F-05)를 더한다. 개발자에게도 채팅과 함께 알림·웹훅으로 밀어 주는 경로를 둔다.

**목표 직무:** LLM·RAG 에이전트 개발자(기업용 AI 플랫폼, 기존 업무시스템 연계). 사람인 LLM·RAG 에이전트 개발 공고 352건(2026-10-27 집계)에서 Python 91%, 에이전트 75%, RAG 72%, 평가·관측 53%, 업무시스템·지식베이스 연계 52%, 공공 14%가 나온다.

**차별점은 세 가지다.** 근거 인용과 문서 최신 여부 표시는 이미 여러 제품에 있어 차별점으로 내세우지 않는다.
1. 단위가 "문서"가 아니라 "**이미 나간 답**"이다. 근거 섹션이 바뀌면 그 답을 받은 사람과 업무시스템에 정정을 보낸다(F-02). 다른 제품은 문서 담당자에게 알린다.
2. 결재 자동화가 아니라, 정책 문서에서 뽑은 표를 **사람이 승인한 뒤에만** 답에 쓴다(F-04).
3. 정책을 **바꾸기 전에** 그 개정으로 무효가 될 답, 달라질 결정표 칸, 알림 받을 사람 수를 정책 담당자에게 보여 준다(F-05). 위 제품들의 공개 문서에서 이런 기능은 찾지 못했다.

"찾지 못했다"는 공개 문서 기준이고, 없다고 증명한 것은 아니다.

### 4-4. 지불 주체와 실재성

- **가설:** 엔지니어링 지식 AI 플랫폼은 엔지니어링 조직이 개발 생산성·플랫폼 엔지니어링 예산으로 산다. 실사용자는 개발자·운영 담당이고, 결재는 VP Engineering 또는 엔지니어링 디렉터가 한다. 지불 주체는 이 한 곳으로 정했고(팀장 결정, 2026-11-12), 구매 의사는 확인하지 못해 가설로 둔다.
- **근거**
  - 시장이 있다: Glean 기업가치 72억 달러(2025-06, Sacra 기재), 영업 대상은 CIO·CTO. Atlassian은 Fortune 500의 80% 이상이 Rovo를 쓴다고 밝혔다(회사 발언).
  - 국내 도입: 국내 기업 생성형 AI 활용 55.7%, 2026 예산 증가 예상 79.3%(AI·IT 담당자 749명, itworld 보도). 올거나이즈 매출 증가 보도(64억 원 → 143억 원)는 공시·공식 출처를 찾지 못했다(전자공시시스템 DART 회사명 검색 결과 없음, 2026-11-12). 그래서 근거로 쓰지 않는다.
  - 예산 위치: LLM 지출 중 혁신 예산 비중이 약 4분의 1에서 7%로 줄고 "정규 예산 항목으로 옮겨 갔다"(a16z 2025, 미국 CIO 100명, https://a16z.com/ai-enterprise-2025/ ). 지불은 중앙 IT와 사업부 예산이 함께 한다고 적었다.
  - 국내 주도 부서: 생성형 AI 프로젝트를 CIO·IT 조직이 주도하는 비율 37.5%, CTO·R&D 26.0%, AI 전담 조직 23.9%(CIO코리아 2026 IT 전략 조사, https://www.cio.com/article/4111617/ ). 주도 부서이고 예산 주체를 물은 것은 아니다.

2. 정책 개정 알림 (웹훅·리콜): 2026-06 이전에 "보안 취약점 이슈는 패치 후 며칠 뒤 공개하나?"에 "30일"로 답했다면, 2026-06-29 커밋(4667e540)으로 "90일"이 되어 그 답을 받은 사람과 도구에 정정이 간다
3. 도구 연동 (API·MCP): 도입 요청 시스템이 "외부 SaaS 3만 달러 도입, 승인 단계가 정책과 맞나?"를 묻는다 → 2023 공개 승인 권한표 기준 Director 승인 후 예산 담당(PAO 또는 VP Finance) 승인. 상위 단계는 아래 단계 승인을 먼저 거친다
4. 보안 정책 (채팅): "위험도 중간인 외부 공급사를 쓰려면 누구 승인이 필요한가요?" → 비즈니스 오너 + VP 이상(2024-01-23 개정, 커밋 0c787db1)

| 질문 | 고른 이유 |
|---|---|
| ① 장애 대응 | 개발 조직이 가장 자주 찾는 런북이고, 역할(Store 기억)에 따라 답이 달라진다 |
| ② 리콜 | 고른 절에 최근 12개월 커밋 1,094건이 있고, 답을 바꾸는 규칙 변경이 12건이다. 권한표는 2021-10~11 개정 커밋(예: "Remove VP from 50 to 250")이 있다 |
| ③ 도입 승인 | 금액 구간과 역할이 표로 정해져 결정표(F-04)를 시험할 수 있다. 경계값(정확히 2.5만·5만 달러)으로 구간 해석을 시험한다 |
| ④ 공급사 승인 | 보안·IT 운영·도입 승인이 함께 걸리는 합동 검토(F-03)로 이어지고, 2024-01 개정이 있어 판 비교도 된다 |

**사용 흐름**
1. 사용자가 로그인한다. 팀과 역할은 장기 기억(Store)에서 불러온다.
2. 한국어로 질문하면 근거 섹션(영어 원문), 판 날짜, 한국어 답을 받는다. 근거가 부족하면 되묻거나 답을 거절한다.
3. 업무시스템(구매 승인 목업)의 "사전 확인"이 플랫폼 API를 불러 승인된 결정표의 결과를 받는다.
4. 여러 팀 관점이 필요한 건은 팀별 에이전트가 검토해 쟁점표를 만든다. 사람이 승인하면 저장된다.
5. 정책 담당자가 개정안(MR)을 올리면, 머지 전에 영향받을 답·결정표 칸·알림 대상 수를 MR 댓글로 받는다(F-05).
6. 정책이 바뀌면 자동 수집이 새 커밋(또는 위키 페이지의 새 판)을 감지하고, 바뀐 섹션을 근거로 했던 과거 답변을 다시 검증해 받은 사람과 업무시스템(웹훅)에 알린다. 링크로 연결된 다른 정책은 관리자에게 함께 볼 후보로 알린다.
7. 관리자는 권한표로 만든 결정표를 원문과 나란히 확인하고 승인한다.

- 전체 핸드북은 72,376청크(같은 기준)라서 절을 골랐다. 법무·인사·채용·보상(행정에 가까움), 마케팅·영업, 아키텍처 설계 문서(14,029청크, 정책이 아니라 설계 문서)는 뺐다.
- 전체 기준 sha256 고유 비율은 97.7%(70,676/72,376)다. 고른 절의 근사 중복 수치는 위와 같고, D1에 수집기로 다시 잰다.
- 비공개 주소(`internal.gitlab.com`)로만 연결된 페이지가 전체 4,195쪽 중 450쪽 있다. 그 링크는 근거로 쓰지 않는다.
- 권한표에는 "승인 기준은 내부 문서 참고(internal only)"로만 걸린 칸이 1개 있다. 결정표에서 뺀다.
- 리콜 시험용 개정 커밋 목록은 `backend/rag/ingest/history.py`가 git 이력에서 만든다.

**수집 규칙:** 공개 저장소를 git으로 받는다(API를 쓰면 요청 간격 1초 이상). 받은 커밋 sha는 스냅샷 안 `collect_manifest.json`과 `data/data.md`(코퍼스 고정 커밋)에 남기고, `data/manifest.jsonl`에는 쪽마다 판 커밋 앞 12자(`version_id`)를 둬 재현할 수 있게 한다. 원문 스냅샷은 `data/corpus.tar.gz`(풀면 `corpus/`)로 두고 코드와 폴더를 나눈다.

**청킹 방식** (두 가지를 비교해 고른다, 가이드 축 ②)

| 방식 | 내용 |
|---|---|
| A. 구조 단위 (주안) | 제목(#~####) 단위로 자르고, 긴 절은 문단을 묶어 약 800자로 나눈다. 긴 절을 나눌 때는 앞 청크 끝 약 120자(15%)를 다음 청크 앞에 겹치고, 청크 앞에 제목 경로를 붙여 잘린 문단도 어느 섹션인지 알게 한다. 권한표는 "표 이름 + 금액 구간 + 역할별 승인" 행 1개를 한 청크로 만든다 |
| B. 고정 길이 (비교 대상) | 약 800자, 앞뒤 100자 겹침 |

청크마다 절, 페이지 경로, 제목 경로, 커밋 날짜, 판 id, 원문 URL, 수집일을 붙인다. 판 필터와 답변 리콜(판 비교)에 쓴다. 서로 다른 청크는 본문 sha256으로 센다(가이드 p.8). **규모(G3)는 겹침 없이 자른 기준으로 센다.** 겹친 청크는 sha256으로 서로 다르게 세져 숫자를 부풀리기 때문이다. 겹침은 검색 품질을 위한 설정이다. 25문항 사전 측정에서 120자 겹침은 주안 방식 hit@5가 같고(0.92) hit@1이 0.76 → 0.80이었다(1문항 차이). 120자를 기본값으로 두고 D2에 골든셋으로 다시 비교해 정한다.

**제외 규칙:** Hugo 단축코드와 사이트 내비게이션은 지운다. 비공개 링크만 있는 칸은 "비공개"로 표시하고 근거에서 뺀다. 답과 manifest에 출처(페이지, 커밋, URL, 라이선스)를 표시한다.

### 10-1. 범용 챗봇 비교 (가이드 p.14 필수 증거)

가이드에 정해진 것은 "같은 질문 5개를 범용 챗봇과 나란히 놓은 비교표"뿐이다. 질문 10개, 챗봇 2종, 채점 칸은 팀이 정한 방법이다.

GitLab 핸드북은 공개 문서라 범용 챗봇이 일부를 학습했을 수 있다. 그래서 차이는 "모른다"가 아니라 **판 날짜와 섹션을 밝히는지, 정책 변경 뒤 예전 답을 고치는지, 근거 없을 때 거절하는지**로 보인다. 챗봇 답은 사람이 챗봇 화면에서 수집한다. 2026-11-10과 2026-11-11에 같은 질문 10개를 범용 챗봇 2종에 5개씩 넣어 수집했고(1~5번은 챗봇 B가 11/10, 챗봇 A가 11/11, 6~10번은 두 챗봇 모두 11/11), 답은 `docs/alternatives/`에, 비교표는 `EVAL_REPORT.md` 10장에 있다. 2026-11-13에는 세 챗봇(챗봇 A: ChatGPT 웹, 화면 모델 표시 "Luna 6". 챗봇 B: Claude Haiku 5.5. 참고: Claude Sonnet 5.5)에 같은 10문항을 한 대화씩 다시 넣었고, 답 전문(`docs/alternatives/chatbot_a_2026-11-13.md`, `chatbot_b_2026-11-13.md`, `chatbot_ref_sonnet_2026-11-13.md`), 대화 공유 링크(각 파일 머리), 전체 화면 캡처(`docs/alternatives/captures_2026-11-13/*.png` 3장)를 함께 두었다.

### 13-3. 미정 사항

아래 번호는 D0 시점의 안건이고, 문장 끝의 현재는 2026-11-10 저장소에서 확인되는 결과다. 현재가 없는 항목은 위 문장 그대로다.

1. **역할 배정과 폴더 주인:** D0 당일 확정(13-1).
2. **README, 시연 영상 3분, Langfuse 스크린샷(G7)의 담당:** D0에 정한다. 현재: README와 Langfuse 화면 캡처는 김승욱이 작성했다(커밋 이력). 시연 영상은 저장소에 없고 담당을 정한 기록이 없다(촬영 D11, 11/16). 상세는 SDD 11-0.
3. **Skill 폴더 이름:** 팀 관점 런타임 Skill 폴더를 `security`, `infra`(인프라·SRE), `itops`(IT 운영), `finance`(재무)로 쓴다. 최종 확인은 D0. 현재: 이 이름으로 `skills/security`, `skills/infra`, `skills/itops`, `skills/finance`가 있다.
4. **결정표 재무 승인 칸:** 권한표에는 업무 승인과 재무 승인이 따로 있다. `DecisionRule`에 칸을 더할지(계약 변경, 3명 승인), `cooperating_depts`로 담을지 D0에 정한다(SDD 11장). 현재: 칸을 더했다(`DecisionRule.financial_approvers`).
5. **파트 사이 계약 세부:** 페이지 id(`rule_seq`) 생성 방식, 결정표 승인자 기록, 섹션 단위 조회 함수, 바뀐 섹션 종류 칸, 청크 본문 해시 칸, 리콜 웹훅 형식과 서명을 D0에 확정한다(SDD 6장, 11장). 현재: 계약은 `backend/schemas/`에 반영되어 있고 필드 추가는 3명 승인 규칙을 따른다.
6. **생성 LLM, 임베딩, 한→영 질의 변환 방식:** D0에 후보를 정하고 D2~D3에 평가셋으로 비교해 확정한다(9장). 현재: 생성은 Haiku 5.5, 임베딩은 `voyage-4` 영어 문장 벡터, 리랭커는 쓰지 않고 질문은 영어로 번역해 검색한다(`EVAL_REPORT.md` 1장, 3장, 8장).
7. **로그인 방식:** D5(11/6) 전에 정한다. 자체 구현(FastAPI + Postgres + bcrypt + JWT 쿠키)을 우선 검토한다(SDD 11장). 현재: 자체 구현으로 정해 `backend/auth.py`에 있다.
8. **숫자 기준:** 13-2를 D0에 동결한다. 현재: 동결 상태이고 결과는 SPEC 3장에 있다.
9. **결정표 변환 정확도 공개 시점:** D0에 합의한다.
10. **두 번째 사용자:** 주 사용자는 개발 조직 그대로 두고, 정책 담당자를 두 번째 사용자로 더해 변경 전 영향 미리보기(F-05)를 주는 것을 D0에 공유한다(4장).
11. **확장 기능 F-05~F-08 범위:** 11/6 중간 점검에서 모두 유지하기로 했다(결정 0059, 0066). 필수 작업이 끝난 뒤 F-05 → F-06 → F-08 → F-07 순서로 진행한다.
