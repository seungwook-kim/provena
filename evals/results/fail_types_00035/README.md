# 배포본 00035-h69 실패 유형 다시 세기 (운영 배포본 저장 행, 코드는 로컬 실행)

결과 파일: `fail_types.json`(전체 숫자), `fail_types.md`(도구가 만든 원표, 도구를 다시 돌리면 덮어쓴다). 이 문서는 설명이라 도구가 건드리지 않는다. 도구는 `evals/retrieval/fail_types.py`, 시험은 `tests/test_fail_types.py`다. `EVAL_REPORT.md` 5장 5-1~5-3이 이 값을 쓴다.

## 무엇을, 왜 셌나

5장 5-1 표는 실패를 "정답이 문맥에 없음(검색)"과 "문맥에 있는데 인용하지 않음(판정·작성)"으로 가른다. 로컬 측정 행에는 답 단계로 넘어간 청크(`retrieved`)가 있어 가를 수 있다. 그런데 **운영 배포본 `provena-api-00035-h69`의 저장 행에는 인용한 청크 id만** 있어 같은 방식으로 못 가른다. 그래서 배포본 행만으로 센 값을 따로 만들었다. 새 LLM 호출도 운영 접속도 없고, 이미 저장된 행(`deploy_latency_*/run*/rows.jsonl`)을 읽는다.

## 어떻게 셌나

- 입력: 배포본 측정 3묶음(v2 50건 x 3회, 검증 20건 x 3회, 새 인용 5건 x 3회)의 저장 행과 평가셋, 코퍼스(`index.tar.gz:chunks.jsonl`).
- 인용 청크 id를 평가셋 정답 위치와 `evals/retrieval/gold.py`의 같은 규칙으로 맞춘다.
- 이름을 일부러 다르게 했다: "정답 위치를 하나도 인용하지 않음"(검색 실패일 수도, 문맥에는 있었는데 인용 안 한 실패일 수도 있음), "정답 위치 일부만 인용".

## 숫자

| 측정 | 관련 행 | 정답 위치를 하나도 인용하지 않음 | 일부만 인용 | 거절 | 정답 밖 인용 (답한 행 중) | 비관련 행 / 그중 답함 |
|---|---|---|---|---|---|---|
| v2 50건 | 75 | 2 (38번) | 4 (36번 1행, 39번 3행) | 1 | 11 / 74 | 75 / 0 |
| 검증 20건 | 30 | 2 (101번, 109번) | 4 (104번 1행, 108번 3행) | 2 | 9 / 28 | 30 / 0 |
| 새 인용 5건 | 15 | 0 | 0 | 0 | 6 / 15 | 0 / 0 |

(위 표는 `fail_types.md` 원표를 줄여 옮긴 것이고 문항 번호별 행은 원표에 있다. 아래 "전후"의 로컬 값은 `EVAL_REPORT.md` 5-1 표에서 옮겼다.)

## 전후

| | 로컬 측정 최종(v2 50건 단일 3회 + 멀티 3회, 5-1 표) | 배포본 00035-h69(위 표) |
|---|---|---|
| 정답이 문맥에 없음(검색) | 0행 | 가를 수 없음. 정답 위치를 하나도 인용하지 않음 2행 |
| 일부만 인용 | 3행(39번) | 4행(36번 1행, 39번 3행) |
| 정답 밖 인용 | 2 / 150 | 11 / 74 |

로컬 최종과 배포본은 행 수·기법이 다르다(로컬 150행은 단일+멀티, 배포본 150행은 질문 50건 x 3회 중 관련 75행). 숫자를 그대로 빼서 "나빠졌다"고 하지 않는다. 정답 밖 인용이 늘어난 몫(8번, 9번)의 원인은 `EVAL_REPORT.md` 5장이 따로 다룬다.

## 한계

- 검색 실패와 판정·작성 실패를 **가르지 못한다**. 앞의 값은 둘의 합이다.
- 사실 질문이 승인·검토 경로로 간 오분류(v2 7, 15, 38번 유형)는 행에 `route`가 없어 세지 않는다.
- 정답 밖 인용은 같은 사실을 되풀이하는 다른 페이지를 인용해도 센다. 내용이 틀렸다는 뜻이 아니다.
- 사람이 인용 내용을 하나씩 판정하지는 않았다.

## 한 줄 재현

```
python -m evals.retrieval.fail_types --out evals/results/fail_types_00035
```

저장된 파일만 읽는다(키·네트워크 없음). 결과 json의 `results` 칸에는 측정했던 PC의 작업 폴더 경로가 들어 있다(저장소 파일 경로가 아님).
