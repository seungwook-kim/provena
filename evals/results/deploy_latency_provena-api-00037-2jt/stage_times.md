# 배포본 단계별 시간 (provena-api-00037-2jt, Langfuse 트레이스)

D8 "비용과 응답 시간을 현재 코드로 단계별 실측"의 운영 측정분이다. 같은 폴더 `stage_times.json`의 요약이며, 값은 `EVAL_REPORT.md` 8장 표의 검색·생성 칸과 "단계별 시간(배포본 `provena-api-00037-2jt`, Langfuse 트레이스, 현재 공식 값)" 단락과 같다.

## 측정 조건

- 대상: 2026-11-11 09시 운영 배포판(Cloud Run 리비전 `provena-api-00037-2jt`, 커밋 `c5ff52e`). 평가셋 v2 50건 x 3회, 문항마다 새 대화, 동시 요청 없음(2026-11-11 09:12~09:26 +09:00, 150건). 요청 보내기와 클라이언트 측 전체 시간은 같은 폴더 `summary.md`.
- 단계별 시간: 그 150건의 트레이스를 팀 Langfuse 공개 API(`/api/public/v2/observations`, 읽기만)로 내려받아 `evals/latency/stage_times.py`로 계산했다. 새로 호출하지 않았다. 내려받은 관측은 3085건, 시간 범위는 2026-11-11T00:12:48Z~00:26:30Z(측정 시간 전체)이고 관측에 남은 세션은 63개다.
- 짝지은 세션: 150건 중 Langfuse에 세션이 남아 요청과 짝지어진 것은 49건(1회 18, 2회 15, 3회 16)이다. 나머지 101건은 짝지을 세션이 없었다. 11/10 밤 운영 배포판(`provena-api-00035-h69`)과 `provena-api-00032-zhs`에서는 150건 중 64건이 남았고 이번에도 일부만 남는 같은 한계가 있으며 원인은 확인하지 못했다.

## 개선 전후

### 단계별 시간: `provena-api-00020` → `provena-api-00035-h69`(11/10 밤 운영 배포판) → `provena-api-00037-2jt`(11/11 09시 운영 배포판)

| 단계 | 00020 p50 / p95 (74세션) | 00035 p50 / p95 (64세션) | 00037 p50 / p95 (49세션) | 00037 - 00035 p95 |
|---|---|---|---|---|
| 검색 | 0.00초 / 1.40초 | 0.00초 / 1.22초 | 0.00초 / 1.02초 | -0.20초 |

| 클라이언트 측 전체 (짝지은 세션) | 10.49초 / 15.59초 | 6.20초 / 10.14초 | 5.04초 / 12.37초 | +2.23초 |

- 00020과 00035 값은 `evals/results/deploy_latency_provena-api-00035-h69/stage_times.md`와 같고, 00037 값은 위 표와 같다.
- 00035와 00037은 서로 다른 세션 집합(64세션 대 49세션)이며 같은 요청을 둘 다 잰 것이 아니다. 생성 p95의 감소(-2.76초)와 클라이언트 측 전체 p95의 증가(+2.23초)가 서로 반대 방향인 것은 위에서 적은 두 세션 때문일 수 있으나 표본이 적어 확정하지 못했다. 생성 시간이 줄어든 몫을 어느 변경의 효과로 나누지도 못한다.

## 한계

- 표본은 150건 중 49건이다. 어느 문항이 남았는지는 정해지지 않았고(질문 번호가 29개) 관련 문항 쪽으로 치우칠 수 있다. 그래서 8장 표 "전체" 행(150건 3회 평균, `summary.md`)과 같은 방식의 값이 아니다.
- 검색 시간과 그래프 전체 시간은 서버가 요청마다 기록하는 칸이 없어 Langfuse 세션 단위로만 계산했다. 150건 전체에서 검색 시간을 재려면 응답에 검색 시간 칸을 더하는 코드 변경과 재배포 뒤 재측정이 필요하다.
- 단계별 비용과 요청별 LLM 호출 시간(`llm_s`)은 서버가 `done.cost_by_step`에 기록한 150행 전체 값이며 `summary.md`·`summary.json`에 있다(8장 "배포본 단계별 비용" 표).
- 이 계산에서도 그래프가 끝난 뒤 시작한 LLM 호출은 생성 시간에서 뺀다(`tests/test_stage_times.py`). 음수 생성 시간 세션은 0개다.
- 원본 트레이스는 질문 원문과 사용자 식별자가 들어 있어 올리지 않았다. `stage_times.json`에는 질문 번호, 대화 식별자, 단계 시간만 있다.
- 8장 표의 승인 대기 칸(29.6밀리초, 55.3밀리초)은 운영이 아니라 로컬 Postgres와 가짜 모델로 잰 값이라 이 문서에 넣지 않았다(`evals/results/d8_stage_report/approval_latency_postgres.json`).
